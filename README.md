# Privacy Analysis of Modern Encrypted DNS

This project investigates whether DNS-over-QUIC (DoQ) and DNS-over-HTTPS/3
(DoH/3) resist traffic analysis better than standard DNS-over-HTTPS (DoH).
The study observes encrypted traffic metadata without decrypting DNS payloads.
It uses packet sizes, timing, burst patterns, directionality, and flow
statistics to measure whether the queried domain or protocol can be inferred.

The current proof of concept was collected on an Airtel network using 50 target
domains across four public resolvers: AdGuard, Cloudflare, Google, and Quad9.
This is a controlled closed-world experiment, not a claim about all domains,
networks, clients, or resolver deployments.

## Research questions

- **RQ1:** Can DoQ, DoH/3, and DoH queries be distinguished using encrypted
	traffic metadata?
- **RQ2:** How does traffic-analysis resistance differ between these protocols?
- **RQ3:** Which packet-size, timing, burst, direction, and flow features
	contribute most to metadata leakage?
- **RQ4:** How does leakage vary across public resolvers and access networks?
- **RQ5:** How do Global and Indian DNS workloads differ in their leakage
	characteristics?

## Environment setup

```powershell
python -m venv .venv

```

The modelling script also imports `xgboost`, `numpy`, and `pandas`. Install them

```powershell

```

`MPLCONFIGDIR` keeps Matplotlib's cache inside the project.

## Required external tools

The capture workflow requires a Windows testbed with:

- Wireshark, including `dumpcap.exe` and `tshark.exe`.
- Npcap, installed with Wireshark, for packet capture.
- The `q` DNS client from `natesales/q`, which supports DoH, DoH/3, and DoQ.

Verify the tools before collecting traffic:

```powershell
dumpcap -D

q --version
```

If Wireshark is not on `PATH`, pass its directory with `--wireshark-dir`. If
`q` is not on `PATH`, pass its executable with `--q-path`. Capture only traffic
generated by the experiment machine and obtain any required network or
institutional permission first.

## Workload generation

Use a pinned Tranco list for reproducible domain selection. The Global workload
takes the highest-ranked domains. The Indian workload selects `.in` domains and
curated India-focused seed domains in Tranco rank order. The default seeds
include Flipkart, Hotstar, IndiaTimes, Jio, Myntra, Paytm, PhonePe, Swiggy,
TataCliq, and Zomato.

For the current proof-of-concept workload:

```powershell
python src\build_workloads.py `
	--tranco-id L5PV4 `
	--count 25 `
	--pool 1000000
```

This creates 25 Global and 25 Indian domains, plus provenance metadata, under
`data/workloads/`. Replace `L5PV4` with the selected pinned list identifier
when reproducing a different collection. Freeze the generated lists for a
collection batch and do not regenerate them between networks or resolvers.

The current Airtel dataset uses three repeats per domain. AdGuard and Quad9
are tested with all three protocols:

```powershell
python src\probe_and_capture.py `
	--iface "Wi-Fi" `
	--network airtel `
	--workload both `
	--all-domains `
	--repeats 3 `
	--resolvers adguard quad9 `
	--protocols doh doh3 doq `
	--wireshark-dir "C:\Program Files\Wireshark" `
	--q-path "C:\Program Files\Q\q.exe"
```

Cloudflare and Google are tested with DoH and DoH/3 only because DoQ attempts
timed out during the Airtel collection:

```powershell
python src\probe_and_capture.py `
	--iface "Wi-Fi" `
	--network airtel `
	--workload both `
	--all-domains `
	--repeats 3 `
	--resolvers cloudflare google `
	--protocols doh doh3 `
	--wireshark-dir "C:\Program Files\Wireshark" `
	--q-path "C:\Program Files\Q\q.exe"
```

Use `--resume` to re-capture entries that are not successful or exceed the
latency threshold. QUIC traffic, especially AdGuard QUIC traffic on Airtel,
may have high tail latency and produce incomplete captures.

Each query produces one PCAP under `data/raw/pcaps/` and one row in
`data/raw/manifest.csv`. The manifest records the network, resolver, protocol,
domain, repeat number, latency, packet counts, server IPs, status, and PCAP
path. Failed, empty, and incomplete captures must be investigated before
modelling.

## Feature extraction

After capture, create the labelled feature table:

```powershell
python src\extract_features.py `
	--wireshark-dir "C:\Program Files\Wireshark"
```

The output is `data/processed/dataset.csv`. Features include packet counts,
packet sizes, bytes by direction, inter-arrival times, flow duration, burst
statistics, and signed sizes for the first 20 packets. IP addresses, ports,
and transport protocol are deliberately excluded because they would expose the
protocol label directly. Captures slower than the 1.5-second default latency
threshold are excluded to reduce bias from truncated flows.

## Analysis

Run the machine-learning pipeline after feature extraction:

```powershell
python src\run_experiments.py
```

The script runs:

- **E1:** Protocol identification with a Random Forest classifier.
- **E2:** Per-protocol domain fingerprinting with XGBoost.
- **E3:** Feature importance and ablation for packet sizes, timing, bursts,
	and the first 20 packets.
- **E4:** Cross-resolver transfer, such as training on AdGuard and testing on
	Quad9.
- **E5:** Global-versus-Indian workload classification and per-workload
	fingerprinting.

Repeated captures are separated by repeat or domain groups where possible so
that the same capture session does not appear in both training and test data.
Results from this closed-world dataset should be interpreted as controlled
evidence, not as general performance guarantees.

## Limitations and scope

- **Single-network bias:** The current dataset uses Airtel only. Jio, campus
	Wi-Fi, and other networks require separate collection.
- **Limited scale:** The current baseline contains 50 domains and a modest
	number of repeats.
- **Protocol availability:** DoQ was collected only for AdGuard and Quad9
	because Cloudflare and Google timed out during DoQ attempts.
- **Connection reliability:** Cloudflare DoH had approximately 17.4% success
	during the Airtel collection, creating class imbalance. AdGuard QUIC also
	had latency-related selection bias.
- **Excluded protocols:** ODoH is not included because it requires a separate
	proxy and target configuration.
- **Padding:** EDNS padding settings were not controlled in this phase.

## Privacy and reproducibility rules

- Use a fresh client process or cleared DNS cache for each query.
- Keep record type, timeout, retry policy, and capture duration fixed within a
	collection batch.
- Record negotiated protocol, resolver, network, client version, date, and all
	failures or retries.
- Do not capture unrelated browsing, synchronization, or background traffic.
- Do not commit PCAP files, CSV datasets, manifests, workload lists, reports,
	credentials, private keys, or other private data.
- Do not claim protocol support unless both client output and the capture verify
	the negotiated transport.
